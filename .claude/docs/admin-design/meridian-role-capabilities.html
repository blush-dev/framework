Capability Sections

Option C, on its own, with the site capabilities drawn the same way: every capability group on the screen is a collapsible section that states in a sentence what the role can do.

Config / Roles / Editor detail screen only not in the prototype

01One shape, top to bottom

The earlier sketch left the screen speaking two languages. Site capabilities were four columns of checkboxes; content types were a list of sentences. Both are the same kind of thing — a named group of capabilities a role either has or does not — so there was no reason for them to look different, and the join between the two panels was the most awkward moment on the page.

Now there is one row: a name, a sentence, and a triangle. Four of them for the site and one per content type below. Open any of them and the checkboxes are underneath, two columns wide, with their keys beside them.

It costs something, and the cost is worth stating. Collapsed, the four site groups are about sixty pixels taller than the four-column block they replace, and nothing on the screen can be read as a column any more — “which types can this role publish” means opening every section. What it buys is a screen you can read rather than decode, at any number of content types, on any width.

02The screen

Operable. Open a section, change something, and the save bar appears; collapse it again and the section says it is holding a change. Check all four theme states, which is what the runbook asks for on anything that touches color.

03Four things the accordion needed

A collapsed section has to say it is dirty

Change Publish anyone’s on Posts, collapse it, and the save bar is counting something nobody can find. So an edited section carries a Changes pill — the same warn pill a live entry with unpublished edits gets in a list, which is the same idea in the same words. It is the one thing an accordion needs that a matrix does not.

Expand all, because eighteen sections is a lot of clicking

The control sits in a screen-level row above both panels rather than in either panel head, because it acts on both. It flips to Collapse all once everything is open, so it is one button rather than two, and the keys toggle sits beside it for the same reason.

You can set a section without opening it

A ⋮ on each row, revealed on hover and always there to the keyboard, carries Full access, Their own only, Read only and No access. Without it the accordion is strictly slower than the list it replaces: setting six types to read-only would be six opens, six scans and twenty-four clicks.

Turning View off quiets the rest instead of hiding it

A type the role cannot see has nothing else to grant. The other seven checkboxes go quiet and a line says why, rather than disappearing — §8’s hidden, not disabled is about an action an account cannot perform, and these are controls you are in the middle of configuring. Products in the fourteen-type stage below is open on that state.

04Three states

Administrator

Administrator holds *. A hundred and twenty-two checked, disabled checkboxes behind eighteen triangles is the menu-of-dead-items problem at scale, so the whole capability area is replaced by one statement — which is also the only honest way to say that types registered next week are included.

Fourteen types

A site running the Shop and Events addons: 122 capabilities. This is the load the current screen is being replaced for, and it is the case where the sentence earns its place — three of these types are invisible to the role and say so in four words.

05What is still open

  • Whether open sections persist per account. Already an open question for disclosure groups generally; this screen makes it pressing, because an operator who opens five types and comes back to all of them closed will not use the screen twice. If it persists it belongs on the account record rather than in browser storage, which makes it an API question.
  • What the roles list shows instead of a count. The collapsed sentence is the most readable statement of a role on this page, and the list and an account’s own screen both need one. That is the list’s decision, not this screen’s.
  • What a type registered later grants. A role that enumerates types goes stale the moment an addon registers one, and nothing on this screen answers it. The safe default is that a new type grants nothing to anyone but Administrator; anything more convenient than that is a security decision rather than a layout one, and it needs a home somewhere on this screen.
  • Whether taxonomy types take the same five actions. A term has no pending-changes state, so Publish anyone’s reads oddly for a tag. Either the word is wrong or taxonomies take a shorter set, and the section would then have two shapes.
  • Whether the section row wants a count after all. The sentence runs long on a type with mixed scopes, and at a glance a reader may want to know only whether anything is granted. A dot, a count, or nothing — this sketch says nothing, on the grounds that the sentence is the readout and a second one beside it is the thing §7 keeps warning about.

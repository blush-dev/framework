Profiles, accounts and bylines

Three nouns, one Profiles collection, and a fallback that resolves by relationship instead of by matching slugs. The screens are the same five the admin already has, with the cleanups listed at the end.

The three nouns

Two ideas were living inside one word. Splitting them is most of the work, and the split lands on the Users section, which holds all three.

NounWhat it isLives inWho sees it
Account Someone who can sign in. Username, email, roles, standing, and the per-account settings — admin theme, light or dark. Users → Accounts Operators
Profile A public identity. An entry of a profile-kind content type, so it has a slug, a status, a Markdown body with components, and the same editor as a page. Its title is the person's name everywhere. Users → Profiles Everyone
Byline The relation between an entry and a profile. A field on the entry, not a screen of its own. One or more per entry. The entry Everyone

An account with no profile is invisible on the site. A profile with no account is a guest. Users is the overarching term and the name of the section; the three things inside it keep their own names, so a screen says account, profile or role wherever it means one of them in particular.

An account has no name of its own. Its name is its profile's title, which is why the same person reads identically in a byline, in the Accounts list and in a conflict notice. The cost is that an account with no profile has only a username to go by, which is the one case the list has to handle deliberately.

One Profiles collection, not one per type

The tempting reading of writing/authors/jane beside interviews/interviewers/jane is two taxonomies with their own terms. That is the reading these screens reject, for one reason: the two Janes would be joined by the string jane and nothing else.

  • A slug is not an identity. Rename it on one and the fallback silently stops resolving, with nothing in the admin to say so.
  • Two people can want one slug. Nothing stops the two archives being different Janes, and no screen would ever show that they are.
  • It multiplies the work. A new avatar, a changed name or a corrected link has to be done once per type, and the admin grows a profile list per type to do it in.

Jane the author and Jane the interviewer are one person with two bios. So: one Profiles collection, and the per-type noun belongs to the content type rather than to the person. Literature calls them Authors, Interviews calls them Interviewers and Photographers, and all three point at the same profile.

How an archive resolves

A content type declares a profile field with an archive base. That gives a URL per profile per field. What serves at that URL is settled in order, and only the first two steps can be content:

1 · Its own index page writing/authors/justintadlock Written for this field. Shown when it exists.
2 · The profile profiles/justintadlock The default body. The canonical URL, and the fallback.
3 · Name and list — Name, avatar, and the entries. No prose.

What this reuses

None of it is a new concept. Step 1 is the index page pattern, moved from “per type” to “per type, field and profile”: an ordinary entry, singular, pinned to an archive URL, created on demand, never counted in a total, with no Duplicate and no Move to trash. Step 2 is the profile entry's own body. Step 3 is what a type's archive does when its index page switch is off.

The constraint that comes with it. Four profiles across three profile fields is twelve possible index pages, nearly all of them empty, and that ratio only gets worse. So they are created on demand only, and there is no list screen for them — they are reachable from the profile they belong to and from the type that defines the field, and nowhere else.

Cleanups these screens make

Against the admin as it stands today. Each one is a rule the project already has, applied where it was not.

Copy and naming

  • New Account → New account. A button says something, so it is sentence case. The Profiles screen already had this right with New profile; the two disagreed.
  • Drafts → Draft. A status tab is named for the status, and the lifecycle is draft / published / scheduled / trash.
  • Under the name → Byline title. The old label described where the value lands rather than naming the field.
  • YOU and YOURS → one marker. Two words for one idea, on two screens, is how a vocabulary starts to drift.

Shape

  • Accounts adopts the Profiles filter row. §7 puts status tabs under the page header and filters in one row below them. Accounts drew its tabs as chips with the search inside the panel, which is the settings-tab shape, not the status-tab shape.
  • One back button, above the title. The account detail carried Your Account and All accounts side by side in the top right; the profile detail put its back button among the actions. §8 asks for a back button naming the collection, and the two screens should not differ.
  • The profile detail's breadcrumb gains its collection crumb. It read Users / Justin Tadlock where the account detail read Users / Accounts / Justin Tadlock.

State

  • Written and Inherited become pills. The column read Introduced by with the prose Its bio and The profile's bio — two phrasings for one state, and no shape to scan. Principle 3 says state carries a shape. The hue is deliberately neutral: a filled dot is its own content, a ring is borrowed, and neither is a status.
  • The self-account notice stops being a warning. Amber is reserved for state. Not being able to change your own roles is an explanation, so it takes the neutral surface — and the copy drops the command-line path, which is not operator-facing.
  • The two missing link states are drawn. Every account in the current data has a profile and every profile has an account, so neither empty state had been designed. An account with no profile and a guest profile are both in the lists below.

What this still does not settle

  • A fourth rail section. §6 says three, and names them, on the grounds that the test for a new one is whether someone would go looking for it by name. Users plainly passes that test — but the rule is foundations' to change, and the diagram in §6 is already wrong by one item.
  • Is a profile a taxonomy-kind type, or a third kind? A term has no pending-changes state. A profile is public prose on a live site, so it almost certainly wants one.
  • Who may edit whose profile. Your own is nearly always allowed; someone else's is editorial. The first capability that depends on the identity of the row rather than on its type.
  • What a byline shows when the author has no profile. The account has no name without one, so there is nothing to render.
  • Whether / belongs to list search. It is in the Profiles search field today and in none of the documents, next to a ⌘K that is already spoken for.
  • Whether a profile can be merged into another. Two guest profiles for one person is the predictable mess, and the fix has no screen.

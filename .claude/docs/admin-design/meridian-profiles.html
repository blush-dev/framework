Profiles design sketch · not a running system

Profiles, accounts and bylines

Three nouns, one collection of people, and a fallback that resolves by relationship instead of by matching slugs. What follows is the structure the four screen sketches assume.

The three nouns

The sketch you described has two ideas inside one word. Splitting them is most of the work, and the split lands cleanly on the sections the admin already has.

NounWhat it isLives inWho sees it
Account Someone who can sign in. Email, roles, credentials, and the per-account settings — admin theme, light or dark. Config → Accounts Operators
Profile A public identity. An entry of a profile-kind content type, so it has a slug, a status, a Markdown body with components, and the same editor as a page. Content → Profiles Everyone
Byline The relation between an entry and a profile. A field on the entry, not a screen of its own. One or more per entry. The entry Everyone

Everything you asked for falls out of that split. An account with no public presence simply has no profile. A guest author is a profile with no account. profiles/jane is content because a profile is an entry, and it is edited the way a page is edited because the project already decided that terms are entries and index pages are entries.

One name has to move. The brief puts the admin theme and the light/dark setting on Your Profile, which makes “profile” mean both a private settings screen and a public page. The settings screen becomes Your Account, which is what it actually is, and “profile” is left to the public thing.

One collection of people, not one per type

The tempting reading of posts/authors/jane beside recipes/cooks/jane is two taxonomies with their own terms. That is the reading the sketches reject, for one reason: the two Janes would be joined by the string jane and nothing else.

  • A slug is not an identity. Rename it on one and the fallback silently stops resolving, with nothing in the admin to say so.
  • Two people can want one slug. Nothing stops posts/authors/jane and recipes/cooks/jane being different Janes, and no screen would ever show that they are.
  • It multiplies the work. A new avatar, a changed display name or a corrected link has to be done once per type, and the admin grows a people list per type to do it in.

Jane the cook and Jane the author are one person with two bios. So: one Profiles collection, and the per-type noun belongs to the content type rather than to the person. Recipes calls them Cooks, Posts calls them Authors, and both point at the same profile.

How an archive resolves

A content type declares a people field with an archive base. That gives a URL per profile per field. What serves at that URL is settled in order, and only the first two steps can be content:

1 · Its own index page recipes/cooks/jane-okonkwo Written for this field. Shown when it exists.
2 · The profile profiles/jane-okonkwo The default body. The canonical URL, and the fallback.
3 · Name and list — Display name, avatar, and the entries. No prose.

What this reuses

None of it is a new concept. Step 1 is the index page pattern, moved from “per type” to “per type and field and profile”: an ordinary entry, singular, pinned to an archive URL, created on demand, never counted in a total, with no Duplicate and no Move to trash. Step 2 is the profile entry's own body. Step 3 is what a type's archive does when its index page switch is off.

The constraint that comes with it. Twenty-four profiles across four people fields is ninety-six possible index pages, nearly all of them empty. So they are created on demand only, and there is no list screen for them — they are reachable from the profile they belong to and from the type that defines the field, and nowhere else. A table of ninety-six mostly-blank rows is the failure mode this rule exists to prevent.

Four decisions the sketches make

Two lists, one link — not a merged People screen

Merging them puts a Config object and a Content object in one table, where a status pill would mean two different things and a row's permissions would depend on which half you were looking at. Cross-section lookup is already solved: ⌘K finds Jane whichever side she is on.

A people field is plural from the start

Recipes wants a Cook and a Photographer. Author is just the first people field, so the type declares a list of them, each with its own label, base and arity. A model where “author” is special breaks on the second one.

Unlinking an account does not delete its profile

Same rule as turning off a type's index page: the switch stops the routing, it does not destroy the entry. An unlinked profile becomes a guest profile and keeps its bylines, which is what you want when someone leaves.

No guest rows in the Accounts list

Widening Account to mean “a person the site knows about” gives one people table, and a list where most rows cannot sign in, have no email and ignore every column the screen is built around. Guests are profiles. The Accounts list stays a list of people who can sign in.

What this does not settle

  • Does a profile carry pending changes? The project says a term has no pending-changes state. A profile is real public prose, so it probably should have one — which means a profile is not quite a term, and the taxonomy-kind shortcut needs a third kind.
  • Which columns a profile list is allowed. Core columns are Title, Status, Author, Updated for every type. Author on a profile is nonsense, so the sketch swaps in Account and Bylines. Terms already do this, but the rule does not say so.
  • Who may edit whose profile. Editing your own is nearly always allowed; editing someone else's is an editorial capability. That is two capabilities the roles screen does not have yet.
  • Where a site-wide Profiles collection sits in the panel. The nesting rule puts a taxonomy used by one type under that type, and one used by several in Structure. Profiles is used by every type with a people field, so the rule exiles it — away from the types whose archives it feeds.
  • What an account's own display name is for once a profile owns the public one. Probably the operator-facing name in audit trails and the Accounts list, which means two names per person and a question about which one an entry's byline shows when there is no profile.

What changed from the entries list

Type-driven variation, not a second component
  • Author becomes Account. A profile has no author, and the one thing you want to know scanning this list is whether the person can sign in.
  • Guest is a tag, not a status. It describes the account link, and the status column already means something else. A dashed avatar carries it a second time.
  • No index row pinned at the top. There is no archive of profiles — /profiles is a container, not a type archive. If that turns out to be wanted, the pinned-row pattern is already there.

Why the base lives here and not on the profile

A profile has one slug and one canonical URL. The words authors, cooks and photographers belong to the types that credit people, so they are declared once per type and apply to every profile — the same move as a type owning its own singular noun for the New button. Nothing about Jane changes when a type renames its field; her archive URL does, and that is a type-level redirect rather than twenty-four profile edits.
